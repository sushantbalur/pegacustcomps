# Security Considerations

> Part of [Cross-Cutting Best Practices](./README.md).

The APIs cataloged in these skills return content that can originate from other users, an AI model, or the current URL — none of it should be treated as trusted by default. The items below call out where that matters, organized roughly by OWASP Top 10 category.

| OWASP category                                | Where it applies here                                                             |
| --------------------------------------------- | --------------------------------------------------------------------------------- |
| A01: Broken Access Control                    | Client-side checks as a security boundary; trusting client-computed permissions   |
| A03: Injection (incl. XSS)                    | Rendering feed/comment/GenAI content; prompt injection into GenAI Assistant calls |
| A05: Security Misconfiguration                | Manually managing auth headers/tokens instead of using the provided REST client   |
| A08: Software and Data Integrity Failures     | Trusting uploaded/downloaded attachment content without a type check              |
| A09: Security Logging and Monitoring Failures | Logging raw error payloads or field values that may contain PII/tokens            |

## Sanitize Free-Text Content Before Rendering It as HTML

Case feed posts/comments (`FeedUtils`), correspondence, and GenAI Assistant replies (`GenAIAssistantUtils.sendMessage`/`sendMessageForAgent`) are free text written by another user or generated by a model — not markup you authored. **NEVER** render this content with `dangerouslySetInnerHTML`/`innerHTML` without first sanitizing it through a library such as `dompurify`. Treat an AI-generated response exactly like user-generated content for this purpose: a model can be prompted (directly or indirectly, via injected content it summarizes) into emitting markup or script, and it is not a trusted source of pre-sanitized HTML.

```typescript
import DOMPurify from 'dompurify';

const safeHtml = DOMPurify.sanitize(feedPost.message);
```

If the content is only ever rendered as plain text (no formatting needed), render it as text content instead of HTML and skip the sanitization step entirely — that's a stronger guarantee than sanitizing and still using an HTML sink.

## Treat Feed Content Forwarded Into a GenAI Prompt as Untrusted Input Too

If a component builds a GenAI Assistant message (`sendMessage`/`sendMessageForAgent`) that incorporates case feed text, attachment names, or other user-authored content, remember that content can itself contain text crafted to influence the model ("prompt injection") — for example, embedded instructions telling the assistant to ignore prior context. Don't concatenate raw user content directly into a system-level instruction string; keep user-authored content clearly delimited as data being discussed, not as instructions to the assistant, and don't let a model's response alone gate a subsequent privileged action (like a submit or delete) without the normal validation/confirmation flow.

## Client-Side Checks Are UX, Never the Security Boundary

Hiding a button, disabling an action, or skipping a client-side field because a role/permission check failed is a UX affordance, not access control. The server (case type stage, access control rules) is the actual authority — never assume that because a component doesn't render a "Delete" button, the corresponding `ActionsApi.deleteWork` call is unreachable, and never treat a client-computed permission flag (from cached state, a prior response, or a stale subscription) as authoritative for anything higher-stakes than what to render. Fail closed: if a permission/config value that gates a sensitive action hasn't loaded yet or failed to load, treat it as "not permitted" rather than defaulting to showing the action.

## Only Build Deep Links From a Trusted `routeKey`

When constructing a shareable link with `SemanticUrlUtils.getResolvedSemanticURL(routeKey, payload, params, locale?)` (see [deep-link-semantic-url](../pconnect-navigation-locale-genai/cookbooks/deep-link-semantic-url.md)), source `routeKey` from `PCore.getSemanticUrlUtils().getActions()` — never from a raw query string, hash fragment, or other user-controllable input. Passing an attacker-influenced value as a route key risks resolving to an unintended destination (an open-redirect-style issue) rather than the case/view you meant to link to.

## Treat Client-Side Upload Checks as UX Only, Not a Security Control

`AttachmentUtils.uploadAttachment` performs server-side size/type rejection — that is the authoritative check. A client-side file-type or size pre-check (to show a fast error before the network round trip) is fine for UX, but never rely on it as the actual security boundary: always still handle the rejection from `uploadAttachment` itself, and never assume a file "passed" validation just because the client-side check didn't flag it.

## Don't Trust Downloaded Attachment Content Either

`AttachmentUtils.downloadAttachment`/`streamDownloadAttachment` return binary content another user uploaded. If a component renders that content inline (previewing an SVG, HTML, or text file, for example) rather than triggering a normal file download, apply the same rule as feed content: an SVG can carry an embedded `<script>`, and an HTML file can carry arbitrary markup. Prefer the browser's native download/save behavior for attachment content, and if inline preview is genuinely required, sanitize it first and never render it as same-origin HTML without isolation (for example, a sandboxed `<iframe>`).

## Let the Provided REST Client Own Authentication

`RestClient` (see [pcore-rest-data-details.md](../references/pcore-rest-data-details.md)) already attaches the operator's authenticated session/auth headers to `invokeRestApi`/`invokeCustomRestApi` calls, and exposes `getHeaderProcessor()` for the supported way to add custom headers. Never manually read, store, or forward an auth token from component code (e.g. into `localStorage`, a query string, or a custom header built by hand) — that both duplicates a security-relevant responsibility the platform already owns and creates a new place a token can leak (browser storage is readable by any script on the page, and tokens in URLs end up in server access logs and browser history).

## Don't Leak Sensitive Details Through Error Handling

When a `Promise`-returning PCore/PConnect method rejects, `ErrorHandler`/`FormUtils` (see [pcore-misc-details.md](../references/pcore-misc-details.md)) let you show a message to the user and/or log the failure. Show the user a clear, actionable, generic message via `ErrorHandler.setGenericFailedMessage`/the component's own error state — never the raw rejection object, a stack trace, or an internal error code that could reveal implementation details. If you log the error for diagnostics, make sure the logged payload doesn't include field values that could contain PII or auth tokens; log identifiers (case ID, context name) instead of full field state.

## Unsubscribe When a Component Loses Access, Not Just to Avoid Leaks

`PubSubUtils.subscribe`/`MessagingServiceManager.subscribe` keep delivering events to a callback until you unsubscribe. Beyond the memory-leak concern already covered in the [data-page-subscription-cleanup](../pconnect-data-subscriptions/cookbooks/data-page-subscription-cleanup.md) and [pubsub-cleanup](../pconnect-data-subscriptions/cookbooks/pubsub-cleanup.md) recipes, unsubscribing promptly on unmount also matters from a least-privilege standpoint — a component that has navigated away from a case shouldn't keep receiving that case's pushed updates in memory for longer than it's displayed.

## Treat User-Supplied Values as Untrusted Before Passing Them as API Parameters

Search boxes, list filters, and other user-editable inputs sometimes feed directly into a data page or REST call parameter (`DataApiUtils`, `RestClient` — see [pcore-rest-data-details.md](../references/pcore-rest-data-details.md)). The server enforces access control on the resulting request, but still validate/constrain the shape of user input client-side before sending it (for example, an expected numeric ID field should not accept arbitrary text, and an expected enum value should be checked against an allow-list rather than passed through) — this reduces malformed-request noise and avoids accidentally surfacing another record's error details in a client-visible error message.

## Practice Data Minimization When Forwarding Content to a GenAI Model

`GenAIAssistantUtils.sendMessage`/`sendMessageForAgent` and `GenAIUtils.rewriteText` (see [pcore-analytics-genai-details.md](../references/pcore-analytics-genai-details.md)) send whatever text you pass to a model, which may be hosted by a third party outside the case's normal data boundary. Don't forward more of the case than the task actually needs — for example, summarizing one field's free text doesn't require serializing the entire case payload into the prompt. Passing an entire case (including fields the current user shouldn't be exfiltrating verbatim into a model's context, such as another party's contact details embedded in an unrelated field) is a data-minimization problem independent of whether the model itself is trustworthy.

## Don't Assume a Case/Assignment ID From a URL Is Valid for the Current User

A deep link, browser history entry, or bookmarked route can carry a case ID, assignment handle, or `routeKey` that the current user is no longer (or was never) authorized to open. The server-side access check on the resulting request is the real control, but the component should treat "the ID resolved to a permission/not-found error" as an expected, handled outcome — not a bug — and show a clear "you don't have access to this" or "not found" state rather than a raw error, a blank screen, or (worse) a partially-rendered view built from a previous, unrelated case still held in memory.

## Be Deliberate About What `EnvironmentInfo` Details You Surface

`PCore.getEnvironmentInfo()` (see [pcore-environment-info-details.md](../references/pcore-environment-info-details.md)) exposes details about the running application/environment. Avoid logging or otherwise surfacing its full contents in a way that ends up in client-visible debug output, error reports, or telemetry sent to a third party — prefer reading and forwarding only the specific field a feature needs (e.g. the current locale) over passing the whole object along.

## Checklist

- Sanitize (or render as plain text) any feed post, comment, or GenAI Assistant reply before putting it in an HTML sink.
- Never let raw user-authored content become part of a GenAI system instruction — keep it clearly framed as data, not instructions.
- Never treat a hidden/disabled UI element, or a client-cached permission flag, as the actual access-control boundary — fail closed on unknown/unloaded permission state.
- Source deep-link `routeKey` values from `getActions()`, never from user-controllable URL input.
- Treat client-side upload/download type checks as UX only; the server's validation is authoritative, and previewed attachment content needs the same sanitization as any other untrusted HTML.
- Never hand-manage auth tokens/headers — use `RestClient`'s built-in mechanisms.
- Show users a generic, actionable error message; log identifiers, not raw field values or tokens.
- Unsubscribe on unmount/navigation-away, not only to avoid leaks but to stop receiving updates a component no longer has a reason to see.
- Validate/allow-list user-supplied values before they become REST or data page parameters.
- Forward only the case content a GenAI call actually needs — don't serialize an entire case into a prompt when one field would do.
- Handle a permission/not-found error from a URL-sourced case or assignment ID as an expected outcome, with a clear message — not a raw error or a stale view left over from a previous case.
- Read only the specific `EnvironmentInfo` field a feature needs rather than logging or forwarding the whole object.
